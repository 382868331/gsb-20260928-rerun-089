# 工业控制编程平台 · 虚拟控制器（首轮）

首轮交付一个**纯虚拟**的可编程逻辑控制器：Go 实现运行核心（校验、扫描执行、
版本管理、HTTP API），React + React Flow 提供梯形图风格的连线编辑与扫描观察
页面。系统不连接任何真实工业设备，所有 I/O 都是 API/页面上的内存值。

## 控制模型

程序是一张有向无环图（梯形图风格），节点类型：

| 节点 | 含义 | 变量约束 |
| --- | --- | --- |
| `rail` | 左电源轨，全图唯一 | — |
| `contact` / `ncontact` | 常开 / 常闭触点 | 读取 `in.*`、`m.*`、`out.*`、`t.*` |
| `or` | 并联支路汇合（≥2 入 1 出） | — |
| `coil` | 线圈（输出或内部保持位） | 只能写 `out.*` 或 `m.*` |
| `ton` | 通电延时定时器，非保持 TON | 名称 `t.*`，`delayMs > 0` |

变量命名空间即扫描区域：`in.*` 输入、`m.*` 内部保持位、`t.*` 定时器、
`out.*` 输出。

## 明确的扫描顺序

调度器以固定周期（默认 100 ms）触发扫描，每次扫描严格执行：

1. **读输入**：触点在逻辑阶段只读取上一扫描提交后的输入/内部/输出/定时器表；
2. **逻辑求值**：从唯一电源轨按拓扑序计算能流（已校验无环）；
3. **定时器更新**：TON 在得能流时累加扫描周期时长，失电清零，新值暂存；
4. **统一提交**：本扫描所有线圈与定时器状态在求值结束后一次性提交，下一扫描才可见。

因此线圈/定时器的级联效果按扫描传播（真实 PLC 语义），观察页显示的输出来自
真实扫描计数与状态表，而非直接写入。

## 定时与保持、暂停/恢复

- `m.*`、`out.*` 与 TON 累计时间都在引擎内跨扫描延续；
- 暂停只是停止调度（不再发生扫描），恢复时使用同一引擎状态，**不重新计时**；
- 单扫描按钮用于逐周期核对能流传播。

## 程序版本与非法连接

- 编辑后点击「作为新版本载入」：后端先做完整校验，通过后版本号 +1 原子切换，
  新版本从初始状态开始扫描；
- 校验失败返回 422 与逐条错误（定位到节点/连线），**旧版本继续运行，非法程序绝不执行**；
- 校验项：唯一电源轨、悬空/不可达节点、连线成环、触点单入（并联必须用 OR）、
  OR 至少两入、线圈/TON 终端无出线、线圈写 `out.*/m.*`、定时器 `t.*`、
  重复线圈/重复定时器、未知节点类型与悬空连线。

## 演示程序：启停互锁 + 延时动作

- 按下 `in.start`：`m.run` 得电，`m.run` 自保持支路将其锁定；
- 常闭 `in.stop` 串联在回路中，按下即断开互锁；
- `m.run` 驱动 TON `t.delay`（1500 ms），暂停期间累计时间冻结；
- 延时到后 `t.delay.Q=1`，下一扫描点亮 `out.lamp`。

## 运行

```bash
# 1. 构建前端（输出到 Go 嵌入目录 internal/api/assets）
cd frontend && npm install && npm run build && cd ..

# 2. 运行（默认 :8080，扫描周期 100ms）
go run . -addr :8080 -tick 100ms

# 开发前端（热更新，/api 代理到 8080）
cd frontend && npm run dev
```

测试：

```bash
go test ./...
```

## HTTP API

- `GET /api/status` 调度状态 + 最近扫描报告（支持 `?wait=1` 长轮询）
- `GET /api/program` 当前版本程序
- `POST /api/program` 校验并作为新版本载入（失败 422）
- `POST /api/program/validate` 仅校验不载入
- `POST /api/program/demo` 重新载入演示程序（新版本）
- `POST /api/run` / `POST /api/pause` / `POST /api/step` 连续扫描 / 暂停 / 单扫描
- `POST /api/inputs` body `{"name":"in.start","value":true}` 置输入表

后续设备接入只需在同一控制模型外增加适配层：设备采样写入输入表、输出表提交后
再映射到设备；本虚拟控制器不包含任何真实工业设备连接。
